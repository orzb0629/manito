# 활동 초기화와 학생 명단 관리

## 적용

Supabase SQL Editor에서 `postgres`로 **005만** 적용합니다.

`supabase/migrations/202611010005_activity_reset.sql`

001~004는 수정하거나 다시 실행하지 않습니다. 005 적용 자체는 기존 학생·기록·학급을 초기화하지 않습니다. 서버·클라이언트를 함께 갱신해야 새 버튼이 동작합니다. 추가 환경변수는 없습니다.

005는 접근이 차단된 `app_private.reset_confirmations` 테이블과 서버 전용 RPC 두 개를 추가합니다. 001에서 만든 상태 전이 가드와 학생 세션 검증 함수는 005에서 교체합니다. 기존 검사를 유지하면서, 트랜잭션에 묶인 초기화 승인에만 잠금 해제를 허용하고 학생 기록 요청은 초기화와 학급 행 잠금을 공유하도록 합니다. 트리거 비활성화나 클라이언트 설정값으로 검사를 우회하지 않습니다.

## 사용

1. 선생님 공간에서 담당 학급을 선택하고 저장하지 않은 설정을 저장하거나 취소합니다.
2. **활동 초기화**에서 삭제 대상을 확인합니다. 명단·일정은 기본적으로 유지하며, 각각 삭제를 선택할 수 있습니다.
3. 다음 단계에서 선택한 항목을 다시 확인하고 현재 학급 이름을 정확히 입력합니다.
4. **확인하고 활동 초기화**를 누릅니다. 취소하거나 첫 단계까지만 진행하면 활동 데이터는 바뀌지 않습니다.

항상 삭제되는 항목: 배정, 미션 완료와 비밀 일지, 서약, 공개·배정 확정 상태, 학생 코드, 학생 로그인 세션, 배정·공개 미리보기 확인 요청.

선택 항목: 학생 명단 / DAY 1~5 날짜와 미션 내용. 학급 이름·학급 소유권·교사 계정은 유지합니다. 명단과 일정을 유지해도 학생 코드를 새로 발급하고 배정을 다시 확정해야 합니다. 기존 CSV의 코드는 사용할 수 없습니다.

학생 명단은 한 줄 또는 쉼표로 구분해 여러 명을 등록합니다(최대 80명). 인원수와 학생별 수정·삭제 버튼, 삭제 확인창은 기존 UI/RPC를 재사용합니다. 배정 확정 후에는 서버와 화면 양쪽에서 명단 변경을 제한하며, 초기화 후 다시 변경할 수 있습니다.

## 서버 경계

- `/api/backend`의 `teacher.prepareReset`, `teacher.confirmReset` 모두 기존 Origin 검사·요청 제한·Supabase Auth 사용자 검증을 통과해야 합니다.
- RPC는 승인 교사·활성 학급 소유권을 확인하고 학급 행을 잠급니다. anon/authenticated에는 실행 권한이 없습니다.
- 확인 요청은 서버 난수의 HMAC만 저장하며, 교사·학급·명단 버전·설정 버전·상태·이름·삭제 선택에 묶이고 5분 뒤 만료됩니다. 새 요청은 이전 요청을 대체합니다. 성공한 요청은 재사용할 수 없습니다.
- 확인 시 이름·버전·상태를 다시 검사합니다. 초기화는 한 RPC 트랜잭션이며, 오류 시 코드·세션을 포함한 모든 변경이 롤백됩니다.
- 명단·설정 버전은 초기화 후 증가하므로 초기화 전 편집 요청을 재사용할 수 없습니다.
- 학생 코드/세션 검증 구조와 교사 로그인 저장 방식은 유지합니다. 학생의 인증된 기록 요청은 초기화와 학급 잠금을 공유하여 이전 요청이 초기화 뒤 기록을 다시 남기는 경합을 방지합니다.
- 데이터 삭제는 선택한 학급으로 한정합니다. 네트워크 오류로 완료 여부를 확인하지 못했다면 학급을 새로고침해 상태를 먼저 확인합니다.

## 검증

`npm.cmd run test:all`에 005 업그레이드 보존, RPC 권한·소유권, 확인 만료·교체·재사용 거부, 이름·버전 검사, 강제 오류 롤백, 코드 재발급·초기화 무효화, 재배정·명단 잠금, 유지/삭제 조합, 다른 학급 격리 테스트가 포함됩니다.

`npm.cmd run test:browser`는 가상 Auth + 로컬 PGlite DB만 사용하여 기존 전체 활동과 초기화 취소·이름 확인·학생 세션 종료·명단 삭제/일괄 등록·일정 삭제를 검증합니다. 실제 Supabase 데이터는 사용하지 않습니다.
